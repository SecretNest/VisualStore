# Milestone 6 · Wrap-up — Task-level plan

> **Resolution:** task-level (see the note at the top of the milestone 3 plan). Expand after milestone 5; several items are measurements on the user's real data rather than code.

**Goal:** VisualStore runs comfortably on the NAS at the one-million-file scale, keeps itself tidy, is documented for a user who did not write it, and has been through a migration and a restore rehearsal.

**Architecture:** No new subsystems. Index quantisation and PCA become settings honoured by `rebuild_index`; a `maintenance` io job runs VACUUM/ANALYZE and removes orphan thumbnails/previews; the image gets a non-root user and a HEALTHCHECK; CI gains the Playwright suite; `docs/user/` is written; the deferred minors from the milestone 1 and 2 reviews are closed or explicitly retired.

**Spec:** [02 §3.1 migration](../design/02-architecture.md#31-initialisation-and-migration), [04 §6.2 maintenance](../design/04-jobs.md), [07 §9.1 restore, §9.5 resources](../design/07-operations.md), [10 Testing (migration test)](../design/10-testing.md), [00 §1.3 acceptance](../design/00-overview.md#13-acceptance-criteria), [11 §13 item 6](../design/11-roadmap.md#13-milestones).

## Decide before expanding

1. Quantisation default: f16 (exact enough, 2 bytes/dim) vs i8 (half the memory). Recommendation: measure recall loss on the eval set from milestone 3; default to f16 and expose `index.quantization`.
2. PCA: train on the profile's own vectors at rebuild time (needs numpy SVD over a sample) vs ship a fixed projection per model. Recommendation: per-profile at rebuild, sample of 100k vectors, stored as `index_meta.pca` blob; off by default.
3. Non-root image user and volume permissions: fixed uid 1000 vs `PUID/PGID` env like linuxserver images. Recommendation: `PUID/PGID` with an entrypoint `chown` of `/data` only when it is empty, documented.

## Global Constraints (additions)

- Every maintenance operation is resumable and idempotent; VACUUM runs only when the free-page ratio exceeds a setting, never on a schedule alone.
- Documentation under `docs/user/` is the only user-facing documentation besides the README; it is English and task-oriented (deploy, initialise and migrate, restore, import, review).
- The migration rehearsal is a test, not a manual step: run the integration pipeline, copy `/data` to another temp root, start with the new root, and assert equal query results plus a successful incremental scan.

## Review Focus

1. Changing `index.quantization` or `index.pca_dims` must trigger a rebuild and must not change any stored vectors in `vectors.db`.
2. `maintenance` must never delete a thumbnail or preview whose file row exists, even if the row's state is `missing`.
3. After a restore of `visualstore.db` from a backup older than `vectors.db`, start-up must detect the mismatch (frames for unknown file ids) and clean or rebuild without manual steps.
4. Running as non-root with a `/data` volume owned by another uid must fail fast with a clear message rather than loop on `PermissionError` inside the scheduler.
5. The HEALTHCHECK must fail when the scheduler loop has not ticked for 60 s, not merely when HTTP answers.

## File structure

```

  index/usearch_index.py        quantization & PCA options, meta recorded
  jobs/compute/handlers.py      rebuild_index honours options
  jobs/io/maintenance.py        vacuum (threshold), analyze, orphan thumbs/previews, frame-row consistency

```

## Tasks

1. Index quantisation and PCA settings + rebuild trigger (Review Focus 1); measurement script `scripts/measure_index.py` writing memory and recall numbers into a report.
2. `maintenance` job and weekly planner (Review Focus 2); VACUUM threshold setting; test with orphan thumbnails and a missing-state row.
3. Start-up consistency check between `visualstore.db` and `vectors.db` (Review Focus 3) with automatic cleanup of frames for unknown files and index rebuild.
4. Scheduler heartbeat, `/api/system/health`, Dockerfile HEALTHCHECK (Review Focus 5); test that a stalled tick turns health red.
5. Non-root image with PUID/PGID entrypoint and permission pre-flight (Review Focus 4); compose updated; README updated.
6. Migration rehearsal integration test (design §12) and restore rehearsal test (backup, delete, restore, start, verify).
7. CI: Playwright job with the server launcher; cache browsers; e2e kept under five minutes.
8. Deferred-minors sweep from the milestone 1 and 2 final reviews: settings range checks already done in M2; remaining items (401 redirect in polling pages, half-open profile creation ordering, compute retry backoff, test-only `fail` type gating, registry set-equality test, `usage_bytes` caching, backup filename second-resolution, jobs list validation, limiter pruning, cookie `Secure` note, concurrent-writer backup test) each get a ticket-style line in the plan when expanded: fix, or retire with a reason in ADR-0007.
9. User documentation under `docs/user/` (six pages listed above) and README trimmed to point at them; plans README; design docs cross-checked against the shipped behaviour with discrepancies recorded as ADRs rather than silently edited.
10. Performance pass on the user's real data: measure the overnight incremental (a few thousand new files) on the NAS, record numbers against [00 §1.3](../design/00-overview.md#13-acceptance-criteria); tune pool size guidance.

## Acceptance

- All [00 §1.3](../design/00-overview.md#13-acceptance-criteria) criteria have measured numbers recorded in the design.
- `docs/user/` lets someone deploy, initialise on a strong machine, migrate to the NAS, restore a backup, import a v1 database and run the review workflow without reading the code.
- The image runs non-root with a working HEALTHCHECK; CI runs unit, integration, build and end-to-end suites.
